# Automatic pagination in the visual CV editor

## Requested behavior

Expanding text or moving a section must reflow the CV and create pages automatically inside the visual editor. Preserve direct on-page editing, Classic as an optional alternative, PDF text selection, fonts, bullets, decorations, AI review, versions, and local draft recovery. Do not modify candidate documents while developing or testing.

The earlier implementation guarded existing page coordinates and rejected overflow. That was an integration constraint, not a PDF format requirement. PDFium exposes `FPDFPage_New`, `FPDFPage_Delete`, object transfer, and content regeneration: <https://pdfium.googlesource.com/pdfium/+/refs/heads/main/public/fpdf_edit.h>. The pinned engine must be tested directly because upstream documentation alone does not prove that a particular WebAssembly export or cache behavior is available.

## Design

- Build ordered flow blocks from native paragraphs and their owned PDF objects. Preserve section order, inline chip rows, attached rules/backgrounds/bullets, and fixed header/footer areas. Infer margins from the existing document rather than changing its template.
- Apply changed rich text using the native engine's actual line layout. A long section can break between paragraphs; a paragraph taller than a page can break at verified line boundaries. Every character and native object must have exactly one destination. Keep a heading with the next body block.
- Use a pure planner to place blocks across existing pages and append matching pages as required. Compact subsequent content after shrink/reorder; remove only verified empty trailing pages generated by the editor.
- Use one native reflow executor for manual edits, AI proposals, accepted AI changes, and section movement. Create pages before resolving object handles, pin every involved page, regenerate source and destination content, and validate save/reopen. Full-document snapshots make the whole operation undoable and roll back any failure.
- Debounced typing previews and AI previews run the same executor in a scratch engine. Display the resulting continuation pages while preserving the live editing buffer and caret. Preview bytes must not enter saved documents, accepted history, or recovery as accepted content. Reject restores the original layout and page count exactly.
- Preserve the existing 20-page/20-MiB limits with an actionable error and intact pending text. Ambiguous or unsupported structures must fail before a partial layout is shown as accepted. Never silently leave linked regions, decorations, or body content behind.

## Bounded tasks and checks

1. `web/public/pdf-editor/page-engine.mjs` and `web/tests/lib/pdf-pagination-engine.test.mjs`: prove page creation/deletion, cache invalidation, line boundaries, subset fonts, whitespace, export/reopen, and exact text conservation using fictional PDFs. Start with failing regressions.
2. `web/public/pdf-editor/pagination.mjs` and `web/tests/lib/pdf-pagination.test.mjs`: pure placement, added pages, paragraph/section splitting, heading retention, compacting, and safe bounds. Test dense sections, chips, and a paragraph larger than one page.
3. `web/public/pdf-editor/reflow.mjs`, the bridge, and native adapter: extract stable object ownership before edits, run an atomic layout, preserve decorations, and share the result between manual/AI/movement paths. Test rollback and page-count history.
4. `web/src/components/documents/visual-pdf-editor.tsx` and message/draft helpers where needed: surface pagination without the former overflow-to-Classic instruction, retain proposal isolation and local recovery, and keep the editor usable while pages grow.
5. Browser fixtures and tests: expand a one-page CV into multiple pages, type again after preview, inspect exported text/styles/page bounds, undo/redo page creation, recover navigation drafts, move a large section, shrink content, and accept/reject an AI rewrite that adds pages. Inspect the rendered result, not only the page count.
6. Independent specification and code review, full web tests, explicitly enabled native browser checks, TypeScript, and production build. Integrate verified changes into main while preserving unrelated work.

The persistent autonomous-implementation skill authorizes bounded subagents and independent review. Supporting `superpowers` skills are unavailable; their design, test-first, execution, and verification stages are followed directly.

## Implementation and acceptance evidence

- Native page helpers create matching PDF pages and mark them with a nonprinting native object. Empty generated pages can be removed after export and reopen; original blank pages remain intact.
- Manual typing, AI preview/accept, and section movement use `reflowDocument`. Exact native line objects preserve selectable text and styles when a paragraph spans pages. Local font fallback prevents missing-glyph boxes when a Chrome font subset does not contain a newly typed word.
- Live editing maps one editable buffer onto the same bounded paragraph layout used for export. Save retries if typing changes while the scratch layout is running, preventing a newer draft from being discarded. History restores complete PDF bytes and page counts.
- White CV backgrounds are recognized from native rectangle, fill, paint order, and visible ink evidence. Colored artwork, unproved shapes, annotation-only continuations, and ambiguous columns remain protected. Header/footer counters are updated and reserved as placement obstacles.
- The one-page fictional browser fixture grows to multiple pages while editing, preserves ninety uniquely numbered sentences and further typing, recovers the unsaved buffer after navigation, saves selectable text inside the original margins, and supports undo/redo. A second scenario rejects and accepts a multipage AI preview, drags the expanded section, then shrinks the document after reopening and removes its empty generated pages.
- The existing two-page production browser scenario covers direct typing, styled text, save failure/retry, section movement and history, AI review, local recovery, version restoration, and Trash/restore. It now waits for asynchronous editing to finish and centers the moved section before dragging, because reflow may relocate it to a different page.
- Rendered exported pages were inspected for margins, section rules, bullets, bold/italic text, and absence of missing glyphs. Fixtures and screenshots contain fictional data only; the candidate document is never written during verification.
- A separate read-only check of the existing three-page CV expanded its summary into four pages in memory. All 59 original paragraphs remained present, all 6,217 resulting native objects stayed within the checked margins, unchanged header objects did not move, and the source bytes remained identical. This caught and fixed font-leading padding being mistaken for overlapping visible content.
- Final merged-main verification: 2,208 web tests passed, 29 environment-gated tests skipped, zero failures. The three full-app production browser scenarios passed separately. All three native editor browser tests and five native reflow regressions passed, including save races, medium-length wrapping, linked header stability, counters, and generated-page cleanup. TypeScript and production build passed. Independent specification and code review approved with no outstanding findings.

Known limits remain explicit: 20 pages, 20 MiB, rotated pages, ambiguous columns/shared artwork, and links or annotations inside content that would move. These limits retain the draft and reject the operation atomically. Ordinary text expansion and section movement no longer require Classic.

## Follow-up: typing and decorated-section regressions

The preceding acceptance checks did not establish pixel identity across preview pages or correct artwork ownership in a real template. A user report showed that a single character displayed a distant page, competency labels detached from their backgrounds after dragging, and an empty-history error remained visible after a later successful move.

Reproduction now uses a fictional three-page document rendered with the shipped CV template, including linked header text, a gradient rule, competency chips, styled roles and native list bullets. Acceptance requires:

- A real pointer click positions the caret after the first comma; typing one character preserves the first page's header pixels and the caret position. Each preview page has independent raster data. A further character must preserve that state during native input and the debounced layout.
- Typing on a later page keeps the visible caret anchored when the editor changes from one page to a stacked preview.
- Chip glyphs remain inside their own backgrounds, bullets remain aligned with their own lines, gradients remain visible, and native painting order survives text edits and section movement. Text-count conservation alone is insufficient.
- Dragging a decorated section can be undone and redone. An extra Undo at the history boundary acknowledges current history without modifying PDF bytes or reporting a failure. A successful action inside the iframe clears a resolved host error.
- Existing pagination, AI review, save races, local recovery, saved versions and document lifecycle checks continue to pass. Candidate PDFs remain read-only throughout development and verification.

The fixes give each preview page its own copied raster, anchor the visible caret when earlier pages enter the preview stack, and retain line transforms during immediate input and input-method composition. Decoration ownership now uses both axes, preserves native painting order, and attaches each bullet to its own line. Existing vector gradient operators are isolated with the correct graphics transform before PDFium regeneration. Pattern-looking strings remain text. Temporary source-font aliases apply only to actual same-family collisions and are cleaned up without changing the main editor's font identity.

Final verification after merging current main: 2,240 web tests passed, 36 environment-gated tests skipped, zero failures. Native browser checks passed 3/3, including per-page pixels, frame-by-frame later-page caret tracking, actual IME composition, and history boundaries. Production build and TypeScript passed. Independent code and specification review approved the final ownership, graphics, font and viewport changes. The seven explicitly enabled full-app production scenarios cover the reported flows plus pagination, AI, save/recovery and document lifecycle.

A separate root check applied the reported one-character edit and competency-section move to the existing CV entirely in memory: three pages remained, all eight chip labels stayed enclosed by their own artwork, the complete word multiset was conserved, and the original bytes remained unchanged. Independent native checks also verified all 24 checked bullets moved by the same amount as their associated text. Per-character native glyph comparisons distinguish the intended embedded font from a wrong same-name face; whole-font hashes are unsuitable because native font synthesis and subsetting rewrite the tables.
